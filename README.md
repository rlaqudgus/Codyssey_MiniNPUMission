# Mini NPU Simulator

MAC(Multiply-Accumulate) 연산을 직접 구현하여 십자가(Cross)/X 패턴을
판별하는 Python 콘솔 애플리케이션입니다.

## 1. 실행 방법

```bash
python main.py
```

실행하면 아래 모드 선택 메뉴가 나타납니다.

```
[모드 선택]
1. 사용자 입력 (3x3)
2. data.json 분석
선택:
```

- **1번**: 3×3 필터 A, B와 3×3 패턴을 직접 콘솔에 입력하면
  MAC 점수, 판정, 연산 시간이 출력됩니다.
- **2번**: `main.py`와 같은 디렉토리에 있는 `data.json`을 읽어
  size_5 / size_13 / size_25 필터·패턴을 일괄 판정합니다.

`data.json`은 `main.py`가 있는 폴더에 함께 위치해야 하며,
경로는 `os.path.dirname(__file__)` 기준으로 자동 계산됩니다
(실행 위치와 무관하게 항상 같은 폴더의 data.json을 찾습니다).

## 3. 구현 요약

### 라벨 정규화 방식
`data.json` 안에는 같은 의미의 라벨이 서로 다르게 표기되어 있습니다.

- 필터 키: `"cross"`, `"x"`
- 패턴의 `expected` 값: `"+"`, `"x"`

`modules/label_normalizer.py`의 `normalize_label()` 함수가 이 표기들을
모두 프로그램 내부 표준 라벨인 **`Cross`** / **`X`** 로 변환합니다.
표준 라벨을 하나로 통일해두면, 이후 MAC 판정 결과와 `expected` 값을
비교할 때 표기 차이(`'+'`인지 `'cross'`인지)를 신경 쓸 필요 없이
`verdict == expected` 한 줄로 비교할 수 있습니다.

### MAC 연산 구현 개요
`modules/mac_engine.py`의 `mac_score()`는 NumPy 같은 벡터화 라이브러리를
쓰지 않고, 이중 for문으로 같은 위치의 값을 곱한 뒤 누적합을 구합니다.

```python
total = 0.0
for r in range(rows):
    for c in range(len(pattern[r])):
        total += pattern[r][c] * filter_matrix[r][c]
```

### 동점 처리 정책 (epsilon)
`judge()` 함수는 두 점수의 차이가 `1e-9` 미만이면 `UNDECIDED`로 판정합니다.

```python
if abs(score_a - score_b) < 1e-9:
    return "UNDECIDED"
```

부동소수점 연산은 계산 순서나 자릿수 표현 방식에 따라
`0.9`와 `0.8999999999999999`처럼 수학적으로는 같아야 할 값이
미세하게 다르게 나올 수 있습니다. 절대값 차이를 그대로 `==`로
비교하면 이런 오차 때문에 잘못된 승패가 갈릴 수 있으므로,
허용오차(epsilon) 이내의 차이는 "사실상 동점"으로 처리합니다.

## 4. 결과 리포트

### 4-1. 실제 실행 결과 (data.json 분석 모드)

```
총 테스트: 6개
통과: 3개
실패: 3개

실패 케이스:
- size_5_1:  동점(UNDECIDED) 처리 규칙에 따라 FAIL
- size_13_2: 동점(UNDECIDED) 처리 규칙에 따라 FAIL
- size_25_1: 동점(UNDECIDED) 처리 규칙에 따라 FAIL
```

### 4-2. 실패 원인 분석

3건의 실패는 모두 **"데이터/스키마 문제"**나 **"MAC 연산 로직 문제"**가 아니라,
**"수치 비교(동점) 문제"**로 분류됩니다. 근거는 다음과 같습니다.

- `size_5_1`: Cross 점수 `0.9`, X 점수 `0.8999999999999999` →
  차이가 `1e-9`보다 작아 `UNDECIDED`로 판정되었고, expected는 `X`이므로 FAIL.
- `size_13_2`: Cross 점수 `7.499999999999997`, X 점수 `7.5` →
  마찬가지로 `1e-9` 이내 차이라 `UNDECIDED`, expected는 `Cross`이므로 FAIL.
- `size_25_1`: Cross 점수 `4.9`, X 점수 `4.899999999999999` →
  동일한 패턴으로 `UNDECIDED`, expected는 `X`이므로 FAIL.

세 케이스 모두 필터가 로드되지 않거나 크기가 안 맞는 등의
**스키마 오류가 아니며**, 두 점수 자체가 실제로 `0.9`와 `4.9` 등
"거의 동일한 값"이 나오도록 필터가 설계되어 있어 부동소수점
연산 특성상 극미한 차이가 발생한 것입니다. 즉 MAC 연산 로직은
정상 동작하고 있으며, **필터 데이터 자체가 의도적으로 동점에
가까운 값을 갖도록 구성되어 있어** epsilon 판정 규칙에 걸린
"정책상 FAIL"입니다. 반대로 `size_5_2`, `size_13_1`, `size_25_2`는
두 점수 차이가 충분히 커서 정상적으로 Cross/X를 판정했고
expected와 일치해 PASS했습니다. 이처럼 실패 원인을
"데이터/스키마 문제"가 아니라 "수치 비교 정책"으로 명확히
분리해서 진단할 수 있었습니다.

(참고: 만약 실패가 0건이었다면, 이는 모든 케이스에서 두 필터의
점수 차이가 epsilon보다 충분히 크게 설계되어 있었고,
라벨 정규화(`'+' / 'x' / 'cross'` → `Cross / X`)가 정확히 동작하여
expected와 verdict의 표기가 항상 일치했기 때문이라고 설명할 수 있습니다.
이번 데이터셋에서는 3개 필터 쌍의 점수 차이가 매우 작게 설계되어
있었기 때문에 실패가 발생했습니다.)

### 4-3. 성능 표 및 시간 복잡도(O(N²)) 분석

```
크기        평균 시간(ms)    연산 횟수
----------------------------------------
3x3         0.001            9
5x5         0.002            25
13x13       0.008            169
25x25       0.030            625
```

MAC 연산은 N×N 크기의 두 행렬을 같은 위치끼리 한 번씩 곱하고 더하므로,
연산 횟수는 정확히 **N²**번입니다(3×3=9, 5×5=25, 13×13=169, 25×25=625).
곱셈과 덧셈은 각각 상수 시간(O(1)) 연산이므로, 전체 MAC 연산의
시간 복잡도는 **O(N²)**입니다.

측정 결과도 이 관계를 뒷받침합니다. 크기가 3→5→13→25로 커질 때
연산 횟수는 9→25→169→625로 늘어나고(약 1.4배 → 6.8배 → 3.7배씩 증가),
평균 시간도 0.001ms → 0.002ms → 0.008ms → 0.030ms로 비슷한 비율로
증가합니다. 즉 크기(N)가 커질수록 시간이 "선형(N)"이 아니라
"N의 제곱"에 비례해서 늘어나는 것을 확인할 수 있습니다.
이 때문에 실제 AI 모델처럼 필터 크기가 수백×수백으로 커지면
연산량이 기하급수적으로 늘어나고, 이를 병렬로 처리하기 위해
NPU 같은 전용 하드웨어가 필요해지는 이유이기도 합니다.
